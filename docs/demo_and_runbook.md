# Демо (5 минут) и порядок действий на контрольном наборе

## Перед выступлением (за 15 минут)

1. Сервер: `.venv/bin/uvicorn backend.app:app --port 8000`, открыть http://127.0.0.1:8000
2. Локальная модель: `ssh student-lab 'squeue -u $USER'` — задача `cqa-vllm` в состоянии RUNNING;
   туннель: `ssh -N -L 8001:$(ssh student-lab cat ~/cqa/vllm_host):8000 student-lab`
3. Все диалоги DEV и контрольного набора уже оценены (оценки берутся из базы — сеть на демо не нужна).
4. Апелляций в базе нет (чистое состояние), во вкладке «Апелляции» — пусто.
5. Заранее открыть вкладки браузера: карточка `#/conv/DEV:p1-ru-009`, звонок `#/conv/DEV:p4-ru-001`, `#/checklist`.

## Сценарий (1 + 2 + 1 + 1 минута)

**1. Интерфейс (1 мин).** Вкладка **Аналитика**: плитки (оценено, средний итог, грубые ошибки), распределение
баллов, исходы по критериям — навести мышь на столбец. Клик по красному чипу грубой ошибки → карточка.
Фраза: «Модель указывает на реплики — код проверяет каждую ссылку и считает каждое число». Затем
**Диалоги** → фильтр KZ → `p1-kz-003`: объяснения на русском, цитаты — на языке диалога; у каждого критерия
видно, какая модель его оценила (Sonnet или Qwen × 5 голосов, точки голосов).

**2. Оценка (2 мин).**
- `p1-ru-009`: «Идентификация — Нет». Клик по чипу `t11` → реплика подсвечена. Показать «Проверенный участок
  t9–t11, действие ожидалось в t11».
- `p4-ru-001` (звонок): «Идентификация — N/A», причина; блок итога: «вес перераспределён (80 → 100)».
  Клик по чипу-доказательству → запись перематывается к реплике. Над транскриптом — волна записи с отметками
  реплик (оператор сверху, клиент снизу, красные — доказательства) и аудио-метрики: доля речи, темп, паузы.
- `p1-ru-022`: красный флаг «Грубая ошибка выявлена (отмечается отдельно)», цитата «Скиньте деньги мне на карту».
  Запасной пример — `p1-ru-029` (оскорбление «Вы вообще читать умеете?»).
- Если спросят про звонки: `p4-ru-002` — реплики t19–t57 (оператор говорит с коллегой, клиент на удержании)
  выделены штриховкой и не оцениваются.

**3. Апелляция (1 мин).** В `p1-kz-008` у критерия «Ведение диалога» → «Оспорить», комментарий. Вкладка
«Апелляции»: видна спорная оценка, комментарий и фрагмент диалога → «Изменить оценку», выбрать ступень, причина →
«Сохранить решение». Вернуться в карточку: исходная оценка зачёркнута, решение, новый итог («исходно X»).

**4. Замена критерия (1 мин).** «Чек-лист» → изменить критерий (например, «Эмпатия» → «Скорость первой реакции»:
«Да — первый ответ оператора не позднее 3 минут после передачи чата», N/A — «оператор не подключился») →
комментарий к версии → «Сохранить как новую версию» → «Применить к набору». Пояснить: заново оценивается только
изменённый критерий (на DEV — 37 с на 65 диалогов), а новую формулировку оценивает Claude Sonnet.
Финал — вкладка **Эксперименты**: 26 вариантов оценки, маршрутизатор 91% на отложенной выборке против 88% у
Sonnet, стоимость vs точность, кривая «человек смотрит 5% — ловит треть ошибок».

## Контрольный набор — одна команда

```bash
scripts/control_run.sh <group_id> 10     # загрузка → маршрутизатор → results/prod/results.json → проверка формата
git add results/prod/results.json && git commit -m "Control results" && git push
```

Проверено на DEV: 65 записей, формат JSON 1.0 соблюдён (validate_results.js). На 10 диалогов — около 2–3 минут, ≈ $0.11.

## Контрольный набор (подробно)

1. Получить `group_id` от организаторов.
2. В интерфейсе: «Загрузить group_id…» → ввести значение → «Оценить весь набор» (модель в шапке).
   Или в терминале (с возобновлением после сбоя):
   ```bash
   .venv/bin/python -m scripts.run fetch --group <ID>
   .venv/bin/python -m scripts.run evaluate --group <ID> --provider router --workers 10   # основной (Sonnet + Qwen×5)
   .venv/bin/python -m scripts.run evaluate --group <ID> --provider local_sc5 --workers 12   # резерв без Claude
   .venv/bin/python -m scripts.run export --group <ID> --out results/<ID>.json
   ```
3. Если Claude упёрся в лимит бюджета или API недоступен — тот же набор оценивает локальная модель.
4. Выборочно открыть 3–4 карточки: цитаты кликаются, объяснения на русском.
5. До 06:00 — финальный коммит и push. После стоп-кода обработку и изменение чек-листа можно делать на
   зафиксированной версии.

## Замена критерия (отдельная проверка)

Вкладка «Чек-лист» → правка (формулировка, тип, вес, N/A, шкала, пояснения) → «Сохранить как новую версию» →
«Применить к набору <ID>». Если критерий связан со временем — модель получает готовые факты
(`first_response_sec`, `max_reply_delay_sec`), сама время не считает.

## Вопросы жюри — короткие ответы

| Вопрос | Ответ |
|---|---|
| Какая модель и сколько стоит одна оценка? | Маршрутизатор: Claude Sonnet 5.5 (контакт, потребность, идентификация, завершение, грубые ошибки) + Qwen3.5-35B на своём GPU с 5 голосами (консультация, эмпатия, ведение). ≈ **$0.011** за диалог по фактическим токенам; только Claude — $0.019; только GPU — $0. |
| Насколько точно? | 89.5% совпадения ответов с эталоном на 44 диалогах (две независимые разметки совпадают на 91.7%). На отложенной выборке маршрутизатор 90.8% против 87.5% у одного Sonnet. Грубые ошибки 7 из 7, ложных 0. Ошибка итога ≈ 7 баллов из 100 (у Sonnet 8.9). |
| Почему не одна модель? | Модели ошибаются по-разному: Sonnet точен в правилах (идентификация 100%), но строже людей на шкалах; Qwen с голосованием лучше попадает в шкалы. Выбор по критериям сделан на одной половине эталона, проверен на другой. |
| Как с казахским? | Чек-лист один, ответы и объяснения всегда на русском, цитаты — дословно на языке диалога. Точность KZ 88.5% — на уровне RU. Если модель пишет объяснение по-казахски, его переводит отдельный шаг. |
| Откуда уверенность, что цитаты не выдуманы? | Каждую цитату проверяет код: реплика существует, текст дословно есть в ней; неверный номер исправляется по тексту; у «Нет» — проверенный участок и ожидаемая реплика. Не прошло — один повтор, затем «Требует проверки». |
| Что если модель ошиблась? | Апелляция → решение проверяющего → пересчёт; видны исходная оценка, решение, итог. Сомнительные оценки (голоса расходятся, сигнал грубой ошибки не подтверждён) помечены заранее: проверка 5% самых неуверенных ловит треть ошибок. |
| Учится ли система на апелляциях? | Проверили: автоматическая подстановка прецедентов в промпт точность не улучшила (90.8% → 87.9%), поэтому выключена по умолчанию. Повторяющиеся решения переносятся в пояснения критерия в редакторе — с проверкой на эталоне. |
| Замена критерия? | Редактор → новая версия → «Применить»: заново оценивается только изменённый критерий (65 диалогов — десятки секунд), его новую формулировку оценивает Claude Sonnet. |
| Звонки? | Запись кэшируется на сервере, перемотка к реплике; Whisper на GPU выровнял реплики по словам (метки ошибались на 6–38 с); доля речи, темп, паузы; разговор с коллегой на удержании не оценивается. |
| Данные клиентов? | Можно полностью локально (GPU, $0). Реальные звонки не публикуются и не лежат в репозитории; ключи и ссылка API — только в .env. |
| Dynamics 365? | Web Components без фреймворка; все данные через один слой `window.CQA.provider` — заменить на Xrm.WebApi; размещение как HTML web resource. |
| Если упадёт GPU или кончится бюджет? | Маршрутизатор сам переключается: GPU недоступен → эти критерии оценивает Claude; лимит Claude → локальная модель. Все оценки DEV и контрольного набора заранее в базе. |
