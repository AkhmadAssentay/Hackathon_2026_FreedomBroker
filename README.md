# CQA — Conversation Quality Analytics (Freedom Broker Hackathon 2026)

Прототип автоматической оценки работы оператора по чек-листу: настройка чек-листа, оценка чатов и звонков на
RU / KZ / EN с объяснениями и ссылками на реплики, апелляция и решение проверяющего с пересчётом итога.

**Главный принцип: модель указывает на реплики, код проверяет каждую ссылку и считает каждое число.**

## Что умеет

| Требование задания | Где в системе |
|---|---|
| Настройка чек-листа: критерии, формулировки, вес, тип ответа (Да/Нет или шкала), N/A, шкала | вкладка **Чек-лист** → «Сохранить как новую версию»; версии хранятся, старые оценки не меняются |
| Оценка выбранного диалога, RU/KZ/EN, бот и система как контекст | карточка диалога → «Оценить», или «Оценить весь набор» |
| Ответ, баллы, вес, объяснение, реплика-доказательство | карточка: по каждому критерию бейдж, баллы после перераспределения, объяснение, чипы-цитаты |
| Пропущенное действие → проверенный участок | для «Нет»: «Проверенный участок t9–t11, действие ожидалось в t11» |
| N/A → причина | серый блок «Причина N/A» |
| Итог, секции, грубая ошибка отдельно | блок итога: балл, проценты секций, флаг грубой ошибки |
| Ссылка ведёт к сообщению / фрагменту звонка | клик по чипу прокручивает и подсвечивает реплику; у звонка перематывает запись. Ссылки вида `#/conv/DEV:p1-ru-009/t11` открываются напрямую |
| Апелляция по критерию с комментарием | кнопка «Оспорить» у критерия |
| Проверяющий видит спорную оценку, комментарий, фрагмент | вкладка **Апелляции**: оценка, объяснение, комментарий и реплики вокруг доказательства |
| Подтвердить или изменить с причиной, пересчёт | форма решения → итог пересчитывается; в карточке видны исходная оценка, решение и финальный итог |
| Контрольный набор и замена критерия | «Загрузить group_id…» → «Оценить весь набор»; правка критерия → новая версия → «Применить»: заново оцениваются только изменённые критерии |

## Быстрый старт

```bash
python3 -m venv .venv && .venv/bin/pip install -r requirements.txt
cp .env.example .env        # вставьте ссылку API организаторов ({group_id} вместо значения) и ключ модели
.venv/bin/uvicorn backend.app:app --port 8000
# открыть http://127.0.0.1:8000 → «Загрузить group_id…» → DEV → «Оценить весь набор»
```

То же из терминала (с возобновлением после сбоя — уже готовые критерии берутся из кэша):

```bash
.venv/bin/python -m scripts.run fetch --group DEV
.venv/bin/python -m scripts.run evaluate --group DEV --provider claude   # или --provider local
.venv/bin/python -m scripts.run export --group DEV --out results/DEV.json
.venv/bin/python -m scripts.run budget                                   # расходы по моделям
.venv/bin/python -m pytest -q                                            # тесты расчёта баллов
```

## Модели и стоимость

Провайдеры за одним интерфейсом (`backend/judge.py`), выбор в шапке интерфейса. По умолчанию — **маршрутизатор**
(`config/router.json`): каждый критерий оценивает модель, которая точнее на нём на половине «dev» эталона —
Sonnet: контакт, потребность, идентификация, завершение, грубые ошибки; Qwen с 5 голосами (self-consistency):
консультация, эмпатия, ведение диалога. Новый или изменённый в редакторе критерий (другая формулировка) оценивает Sonnet.
Если голоса Qwen расходятся (большинство < 60%), критерий помечается «Требует проверки».

| Провайдер | Модель | Когда | Стоимость |
|---|---|---|---|
| Claude API | `claude-sonnet-5-5`, `claude-haiku-5-5` | маршрутизатор / только Claude | считается по фактическим токенам каждого вызова, см. вкладку «Модель и расходы» и `docs/metrics.md` |
| Локальная | `Qwen3.5-35B-A3B` (GPTQ-Int4) на 1× RTX 5000 Ada 32 GB через vLLM | данные не покидают контур; резерв при недоступности API | $0 за вызов (своё железо) |

* Жёсткий лимит расходов на Claude: `CLAUDE_BUDGET_USD` (по умолчанию $4.50). Перед каждым вызовом резервируется худший
  случай (вход + max_tokens), вызов, который может превысить лимит, не выполняется.
* Один запрос на диалог оценивает все критерии; у каждого критерия свой слот в JSON-схеме, поэтому ответ ограничен
  допустимыми значениями именно этого критерия. После правки чек-листа запрос содержит только изменённые критерии.
* Локальный сервер: `hpc/vllm_serve.sbatch` (Slurm), доступ через SSH-туннель на `LOCAL_LLM_BASE_URL`.

## Как считается балл (`backend/scoring.py`, тесты `tests/test_scoring.py`)

1. N/A — только там, где он разрешён и выполнено условие.
2. «Да» = полный вес, «Нет» = 0; шкала — пропорционально весу (верхняя ступень = полный вес).
3. Критерии с N/A исключаются, их вес пропорционально перераспределяется, максимум остаётся 100.
4. Итог округляется до 2 знаков (ROUND_HALF_UP). Нет применимых критериев с весом — итог не рассчитывается.
5. Грубая ошибка отмечается отдельно (политика `flag`; в настройках можно включить `zero_total`).
6. Секции считаются по той же формуле внутри секции.

Модель никогда не считает баллы.

## Архитектура

```
Организаторы (GET group_id) ──► backend/datasource.py  нормализация, факты по времени, аудио
                                        │
config/checklist_v1.json ──► версии чек-листа (SQLite)
                                        │
            backend/judge.py  промпт → Claude / локальная модель → JSON по схеме
                                        │
            валидатор: реплика существует, цитата дословно из неё, у «Да» есть реплика оператора/системы,
            у «Нет» есть проверенный участок и ожидаемая реплика, у N/A есть причина
            → один повтор только для ошибочных критериев → иначе «Требует проверки»
                                        │
            backend/scoring.py  баллы, перераспределение, секции, грубые ошибки
                                        │
            SQLite: оценки (неизменяемые), кэш по критериям, апелляции и решения, журнал расходов
                                        │
            FastAPI ──► frontend/ (Web Components, без сборки)
```

* **Факты из времени считает код** (`facts()`): время первого ответа оператора после передачи, самое долгое
  ожидание ответа, системные события. Модель получает их готовыми и не считает время сама.
* **Звонки.** `audio_url` отдаёт HTML-плеер с подписанной ссылкой на MP3, которая действует 1 час. Сервер
  получает MP3 один раз, хранит его в `data/audio/` и отдаёт с поддержкой Range, поэтому запись можно перематывать.
  Время реплики в записи вычисляется с учётом пауз записи («Запись приостановлена/возобновлена»).
* **Удержание и консультация в звонках.** Пока клиент на удержании, оператор говорит с коллегой: такие реплики
  помечаются как внутренние, показываются в транскрипте отдельно и не оцениваются.
* **Сигналы грубых ошибок из кода.** Фразы вида «переведите мне на карту», «дайте личный номер … платно»,
  оскорбления ищутся регулярными выражениями (RU/KZ/EN) и передаются модели как подсказка. Если код нашёл
  признак, а модель грубую ошибку не подтвердила, критерий помечается «Требует проверки».
* **Память апелляций.** Решения проверяющих с причинами добавляются в промпт как прецеденты для того же критерия
  при следующих оценках.

## Эксперименты (`eval/experiments.py`)

```bash
python -m eval.experiments run qwen_sc5          # вариант: qwen, qwen_sc5, qwen_sub, qwen_percrit, qwen_gloss, gemma, haiku, sonnet, ...
python -m eval.experiments report                # таблица dev/test, комбинации (жюри, каскад, маршрутизатор), риск-покрытие
python -m eval.experiments promote router_sonnet_qwensc5   # записать выбор маршрутизатора в config/router.json
```

Эталон делится детерминированно на `dev` и `test`; способ выбирается только по `dev`. Что проверено:
self-consistency (5 голосов, Wang et al. 2023), подвопросы с правилами в коде (CheckEval / TICK), критерий на запрос,
жюри из моделей разных семейств (PoLL), каскад с эскалацией по неуверенности (Trust or Escalate), маршрутизация по
критериям, глосса KZ→RU. Сырые ответы моделей — в `eval/runs/` (не в git: содержат цитаты).

## Аудио звонков

* Волна записи с отметками реплик оператора/клиента и реплик-доказательств; клик — перемотка.
* `hpc/whisper.sbatch` — Whisper large-v3-turbo на GPU даёт время каждого слова; реплики транскрипта
  сопоставляются с потоком слов (`backend/audio_align.py`), и переход к реплике становится точным.
  Из выравнивания: доля речи оператора и клиента, темп речи (слов/мин), самые длинные паузы.

## Встраивание в Dynamics 365

Интерфейс — набор Web Components (`frontend/app.js`) без фреймворка и сборки. Все обращения к данным идут через
`window.CQA.provider` (`frontend/data-provider.js`). Для Dynamics 365: разместить файлы как HTML web resource и
заменить `RestDataProvider` на реализацию тех же методов через `Xrm.WebApi` / Dataverse custom API.

## Проверка качества

`eval/gold_labels.json` — эталонная разметка 44 диалогов DEV (17 RU, 12 KZ, 12 EN чатов и 3 звонка) по 8 критериям,
сделанная независимо от промптов оценщика. Это объединение двух независимых разметок (A — этот репозиторий,
B — Node-прототип); на 9 общих диалогах они совпадают в 91.7% ответов — ориентир «потолка» для модели,
расхождения разобраны и записаны в файле. `python -m eval.metrics --model <модель>` считает: точность и каппу по критериям,
точность по языкам, ошибку итогового балла, точность/полноту N/A, найденные грубые ошибки, направление ошибок
(ложное «Да» / ложное «Нет»), долю валидных цитат с первой попытки, стоимость. Результаты: `docs/metrics.md`.

## Состав репозитория

* Корень — основное приложение (Python, FastAPI, SQLite, Web Components).
* `alt/node-prototype/` — параллельный прототип на Node.js (репозиторий `cqa-freedom`, слит сюда вместе с историей).
* **Веб-демо на Vercel** (`vercel.json`) показывает Node-прототип в режиме «только просмотр»: сохранённые результаты оценки 60 синтетических чатов DEV (`alt/node-prototype/public/snapshot.json`). Звонки — реальные разговоры клиентов, поэтому в публичное демо не входят.
  Из него перенесены обработка удержания в звонках, сигналы грубых ошибок и вторая эталонная разметка.
  Запускается отдельно: `cd alt/node-prototype && npm start` (порт 3000), подробности в его README.

## Данные и безопасность

* Данные организаторов, записи звонков и база не хранятся в репозитории (`data/` в `.gitignore`). Ссылка API и
  ключи лежат только в `.env`.
* Для продакшена: маскирование ПДн до отправки во внешний API или локальная модель (уже поддерживается).

## Ограничения

* Эталонная разметка небольшая (33 диалога, одна разметка): цифры — оценка, а не гарантия.
* Казахский язык и смешанные RU/KZ звонки — самая рискованная часть; результаты по языкам показаны отдельно.
* Интонацию и дикцию по звуку система не оценивает: запись доступна в плеере для проверяющего.
* Сопоставление времени реплик и записи звонка приблизительное (±несколько секунд).
